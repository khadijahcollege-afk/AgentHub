# AgentHub 1.9.11

Satu BOM di `config.json` tidak lagi menghapus token dan port pengguna.

## Masalahnya

Ditemukan saat menguji paket portable 1.9.10. Config uji ditulis oleh PowerShell,
dan server mengabaikannya sepenuhnya — hidup di port 7788 dengan token yang baru
dibuat. Penelusurannya pendek:

```js
export function readJson(name, fallback) {
  try {
    return JSON.parse(fs.readFileSync(file(name), 'utf8'));
  } catch {
    return fallback;          // BOM ditolak JSON.parse → dianggap "tidak ada berkas"
  }
}

export function loadConfig() {
  const cfg = readJson('config.json', null);
  if (cfg) return { ...DEFAULT_CONFIG, ...cfg };
  const fresh = { ...DEFAULT_CONFIG };
  writeJson('config.json', fresh);   // ← config pengguna DITIMPA
  return fresh;
}
```

`JSON.parse` menolak BOM (`Unexpected token '﻿'`), `readJson` mengembalikan
`null`, `loadConfig` menyimpulkan "belum ada config", membuat config baru dengan
token acak dan port 7788, lalu menimpa berkasnya.

Akibatnya bukan kosmetik. Token akses dan port yang sudah diatur hilang, dan
gejalanya menyesatkan: server tetap hidup dan tampak normal, hanya di alamat lain
dengan token lain. Pengguna akan mengira pengaturannya diabaikan atau UI-nya rusak,
bukan mengira berkasnya tidak terbaca.

BOM bukan hal eksotis di Windows. Notepad menuliskannya, dan begitu juga
`Set-Content -Encoding utf8` di PowerShell 5.1. Berkas JSON yang pernah disunting
tangan sangat mungkin memilikinya. BOM tidak pernah sah **di dalam** JSON
(RFC 8259 mengizinkan UTF-8 tanpa BOM), jadi membuangnya di pembaca adalah
penanganan yang benar — bukan pelonggaran.

## Yang berubah

- **BOM dibuang sebelum `JSON.parse`** (`lib/store.js`). Satu tempat, berlaku untuk
  semua berkas yang dibaca lewat `readJson`: config, koleksi, thread, key, snapshot.
- **Berkas tidak ditulis ulang hanya karena dibaca.** Membaca config bukan alasan
  untuk menyentuh berkasnya; BOM pengguna tetap di tempatnya.
- **Config yang benar-benar rusak disisihkan, bukan dihapus.** Bila `config.json`
  ada tetapi tidak bisa diurai, isinya dipindahkan ke `config.json.rusak-<waktu>`
  lebih dulu, baru config baru ditulis. Server tetap harus bisa jalan — tetapi
  satu-satunya bukti yang bisa dipakai memulihkan token tidak boleh ikut lenyap.
  Menghapus data pengguna diam-diam bukan perbaikan.
- **JSON rusak tetap dianggap rusak.** BOM dimaafkan; `{"a": 1,, }` tidak. Menelan
  kerusakan nyata hanya akan menyembunyikannya sampai suatu hari ia muncul sebagai
  masalah lain.

## Bukti

Penyimpanan diuji langsung: `config.json` ber-BOM dengan token `token-asli-...`
dan port 9761 dimuat — token dan port bertahan, berkas tidak ditimpa. Sebelum
perbaikan, eksperimen yang sama menghasilkan token acak dan port 7788.

Lalu ujung-ke-ujung lewat server sungguhan dengan `config.json` ber-BOM:

```
server hidup di port config : true
port 7788 (default)         : kosong, benar
token acak ditolak         : ya
token pengguna diterima    : ya
port yang dilaporkan config: 9771
token yang dipakai server  : token pengguna
berkas sisihan terbuat     : tidak (benar, config terbaca)
```

Dua pemeriksaan di probe pertama gagal, dan keduanya kesalahan probe: `/api/config`
tidak ada (rutenya `/api/state`), dan pembanding `'ERR'` tidak cocok dengan
`'ERR fetch failed'`. Diperbaiki di alat ujinya, bukan dengan melonggarkan
pemeriksaan.

## Penjaga

Empat penjaga baru di `test/store.test.js`: BOM pada config, BOM pada berkas
koleksi, config rusak disisihkan beserta isinya, dan JSON rusak tetap memakai
fallback. Diuji dengan empat mutasi — BOM berhenti dibuang, `stripBom` membuang
karakter pertama apa pun, config rusak ditimpa, dan berkas sisihan dikosongkan —
dan 4/4 tertangkap.

## Catatan

Dua berkas tes (`instructions-api`, `subagents-api`) dipindahkan ke helper
`startTestServer()`. Keduanya memakai `spawn` langsung, sehingga kegagalan boot
sesekali hanya terlihat sebagai berkas tes yang mati ~100 ms tanpa sebab. Helper
menyimpan keluaran server dan menyebut penyebabnya: port terpakai, crash setelah
boot, atau modul gagal dimuat.

Installer AgentHub belum ditandatangani secara digital. Windows akan menampilkan
peringatan SmartScreen pada pemasangan pertama.

Suite: 677 tes, hijau.
