## What's new

The send button used to have a hole in it. Press it while a run was still working and
the text you had just typed was gone — refused with `409 RUN_IN_PROGRESS`. That is
the correct answer for an API caller and the wrong answer for a person.

- **A message queue that belongs to the server.** Pressing send during a run now
  queues the message instead of rejecting it. The queue lives in `queue.json`, so it
  survives a reload and reads identically from every tab, and the next message starts
  on its own when the current run finishes — from the `done`, `error`, `stopped` and
  post-crash paths alike, because the drain hangs off a single idle hook rather than
  four separate call sites. Bounded at 20 messages per thread: this is for a few
  follow-ups, not for stacking a night of work.
- **Nothing is deleted until its run actually starts.** The order is
  `reserve → start → commit`. If the start fails — the thread is gone, a hook refuses
  the prompt, `runs.begin` rejects — the item returns to its exact position with all
  its content. Deleting first would lose a message that never ran, and no error
  message makes that acceptable. Reservations expire after 20 seconds, so a tab that
  closes mid-reserve cannot freeze the queue.
- **Retries that don't run twice.** Every send carries a `clientCommandId`, and the
  claim is recorded *before* the run begins. A retry after a dropped connection is
  answered from that ledger with `duplicate: true` and the id of the message that
  already accepted it — the model is not called again and the conversation does not
  get a second copy. The claim is released when a run never started, so fixing a
  rejected prompt still works.
- **A phone-sized thread payload, on request only.** `?messageLimit=` and
  `?byteBudget=` are opt-in query parameters; without them the response is exactly
  what it was, so the desktop payload is untouched. When asked, the largest assistant
  reply is trimmed first, user and subagent messages are never touched, a preview is
  never shorter than 2,000 characters, and `refId` points at the *original* message
  index — so fetching the full body can never return the wrong message.
- **The queue is visible where you press send.** Rows sit inside the composer, not in
  a toast that disappears: number, preview, remove, clear. The send button is never
  disabled — during a run it says "send to queue".

Three real bugs were found by auditing the UI rather than by tests, and all three are
fixed. `/stop` finished the run while its process was still alive, so `finish` ran
twice and the second call landed *after* the drainer had started the next run — the
thread that had just run normally was recorded as `error`. `renderChat` scrolled
`#chat-messages`, which has no overflow, so a long thread opened at the top with the
composer 36,000px below the fold (the real scroller is `#chat-scroll`). And a tab that
did not start the run never learned it was running, so its send was refused instead of
queued; the server is the authority now, and `RUN_IN_PROGRESS` means "queued".

Nothing from ZCode's chat-bot side came along: no Telegram/Feishu/Weixin channels, no
bot tokens, no polling, no message cards. This app has no bot, and the queue is
useful without one.

Validated with 534 tests, including pure queue/ledger/budget suites and real-server
tests that wait for a drained run to actually answer; plus UI audits at
1440/1024/390/320 in both languages. See
[CHANGELOG.md](https://github.com/khadijahcollege-afk/AgentHub/blob/v1.7.4/CHANGELOG.md)
for details.
