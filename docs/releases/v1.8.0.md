## What's new

Every command used to live inside a run. `run_command` waited for it to finish and
carried the whole output back into the model's context. That works for `git status`,
and it fails for exactly the work an agent does most: `npm install` printing tens of
thousands of lines, `npm run dev` that never finishes, a whole test suite that takes
minutes. Keeping that in memory means one command can spend the memory the server
shares with every thread; cutting it off with a timeout means real work gets sliced
in half. Now a command can run as a task that outlives the run, with its output kept
in a file you can read again later.

- **A background task is a task, not a run.** The run finishes and the command keeps
  going. Tying task lifetime to run lifetime would kill exactly the commands the
  feature exists for. Its machine is a separate one — `running → done/error/stopped`
  — with no way back: a finished task stays as data, and running it again means a new
  task with a new id, never a reopened one.
- **Output goes to a file, never memory.** `<cwd>/.agenthub/tasks/<id>.log`, inside
  your workspace but outside the tracked tree. It survives the run ending, the tab
  closing, and a server restart. What the model reads back is the **tail** — errors
  and summaries live at the end — and the result is flagged `truncated` so it does not
  assume it read everything.
- **The record survives, the process does not — and that is on purpose.** After a
  restart, a task recorded as `running` is shown as `error` with `recovered: true`
  and its log untouched. Leaving it `running` makes the agent wait for a process that
  no longer exists; deleting the log throws away the only trace of where the command
  stopped, and the agent would start `npm install` over from zero without knowing the
  earlier attempt was half done.
- **Limits protect the machine, not just the conversation.** Three active tasks per
  thread, eight total, a one-hour lifetime, 24-hour retention, twenty records per
  thread. A running task is **never** pruned — dropping the record of a live process
  is what makes it impossible to stop. The numbers the panel shows come from the
  server, so the UI cannot promise more than the server allows.
- **Three tools, one job each.** `start_background_command`,
  `check_background_command`, `stop_background_command`. There is no fourth "wait"
  tool: waiting is a parameter of `start` (`waitMs`), because a separate wait tool is
  precisely what a model would use to sit still longer than it needs to. Short
  commands therefore finish in place and come back complete on the first call.
- **Permissions follow what the tool actually does.** Starting is gated exactly like
  `run_command` — asks in build/edit, danger-checked in guarded, denied in plan.
  Checking reads a file, so it is a read tool and stays available in plan mode.
  Stopping only *revokes* capability, so it is always allowed, plan mode included:
  without it, a task started before you entered plan could never be stopped from
  inside plan.
- **A subagent's task belongs to the parent thread.** That is where it will be read
  and where its id has to be stoppable. Recorded under the child's own id, the task
  would vanish the moment the child finished.
- **A panel for all of it** — `#bg-panel`, opened from a toolbar button that carries
  a live count. List on the left, output on the right, a stop button on each running
  row. It reads the same routes the model uses, so what you see and what the agent
  sees cannot diverge, and it keeps polling only while something is actually running.

Two bugs came out of auditing the panel rather than trusting it. Clicking a row set
the title but left the output box saying "no command selected yet" until the request
returned — indistinguishable from a click that did nothing, so the box now shows a
loading state. And overlapping requests could land out of order, letting a slow
answer overwrite a newer selection; list and detail now each carry a sequence number
and stale responses are dropped. On screens under 860px the two-column layout also
left the output box about 35px tall — present, but unreadable — so the stacked layout
gets more height instead of less.

Validated with 596 tests, including a pure rules suite, a suite that runs **real
processes** (stop really kills the process tree, output really lands in the file with
a real byte count), and a real-server suite that restarts with a seeded registry and
reads a task from the previous process back. Plus UI audits at 1440/1024/390/320 in
both languages, checking geometry rather than screenshots. See
[CHANGELOG.md](https://github.com/khadijahcollege-afk/AgentHub/blob/v1.8.0/CHANGELOG.md)
for details.
