## What's new

Plan mode used to be a switch you flipped yourself, on the access chip. The agent
could not decide that a task deserved planning first, and there was nothing to
approve — so "agreed" meant agreeing to nothing, and once the run continued there
was no record of what had been agreed. Now the agent can ask to plan, hand you a
document, and only start changing files after you say yes.

- **Entering plan mode never asks; leaving it always does.** `EnterPlanMode` only
  *removes* capability — no writes, no commands — so a prompt would be a click for
  nothing, and clicks for nothing are how people learn to dismiss the prompts that
  matter. `ExitPlanMode` restores write access, so it always asks, including in
  `yolo`. Calling it outside plan mode is denied with `NOT_IN_PLAN_MODE`: the call is
  well-formed but illegal, and a silent `allow` would leave the model believing it had
  approval it never received.
- **An empty plan is a schema error.** Whitespace is not a plan. Accepting it means
  "approve whatever I do next", which is the exact thing the card exists to prevent.
  Plans are capped at 20,000 characters — beyond that it is a document nobody reads
  before clicking approve.
- **The plan is a file, and the file is written before the mode changes.** Approved
  plans land in `<cwd>/.agenthub/plans/plan-<thread>.md` atomically, deliberately
  outside the tracked tree. If the write fails, the run stays in plan mode: otherwise
  a run could change files while the agreed record of *what* it would change does not
  exist. After a context summary folds the conversation, the plan file reference is
  re-injected, so a compacted thread does not silently re-plan from scratch.
- **Approval re-opens the tool list.** The tool list is rebuilt when the mode changes,
  so write tools reappear after approval. A model that only sees read tools concludes
  the work is impossible — even though the permission is right there.
- **The plan card renders a document, not a string.** Plans are almost always
  headings and numbered steps, so the card has its own small renderer: without it
  you would approve a page of literal `##` and `-`.
- **The mode you came from is remembered.** Leaving plan from `yolo` returns to
  `yolo`, not to `build`. Falling back to the default would quietly tighten every
  later run.
- **Approve is not allow.** Plan decisions use `approve`/`reject`, not
  `allow`/`deny`: approving a plan is not approving one tool call, and sharing the
  vocabulary would let an old payload approve a plan. `reject` keeps the run in plan
  mode and passes your reason back, because "no" must not behave like "yes" for a
  permission gate. The card waits 15 minutes — longer than a permission (3) or a
  question (10), since you are reading a document.
- **A subagent cannot approve its own plan.** `askPlan` is not inherited. Approving a
  plan raises the write permission for the rest of the run, and a child must not be
  able to raise its own ceiling through a card meant for the parent. A child that
  calls `ExitPlanMode` takes the no-client path and stays in plan mode.
- **`allowedPrompts` are a description, not a permission.** One lax category
  ("install dependencies") would cover any command. Permissions stay one card per
  call.

One real bug came out of auditing the UI rather than the tests: the plan card
inherited `max-height: 100%` from the base `.ask-card` rule, and a percentage
against an `auto`-height parent is simply ignored — so the plan text grew past the
card, was clipped by the host's `overflow: hidden`, and buried the Approve button.
The plan card now carries its own `46vh` ceiling (44vh under 560px), which makes the
body actually shrink and scroll while the header and footer stay visible.

A second, latent bug surfaced on the way: `SessionStart` hook context was appended
straight onto the system message, but that message is now rebuilt every turn because
the mode can change mid-run — so the instructions given at the start of the run
disappeared exactly when the model began working. The context is now stored as part
of the system message that gets rebuilt.

Validated with 560 tests, including a pure plan suite and real-server tests that
approve a plan, write the plan file, and then write the planned file in the *same*
run; plus UI audits at 1440/1024/390/320 in both languages. See
[CHANGELOG.md](https://github.com/khadijahcollege-afk/AgentHub/blob/v1.7.5/CHANGELOG.md)
for details.
