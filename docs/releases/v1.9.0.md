## What's new

The updater downloaded a file and called it ready. Nothing ever asked whether the
bytes on disk were the file the release actually published. `release.yml` has
produced `SHA256SUMS.txt` for every release, and not one line of code read it. So a
download cut short by a proxy, or an HTML login page from a hotel Wi-Fi captive
portal, could be saved as `AgentHub-Setup.exe` and offered with a button that said
"Install now". The install would fail in a way that looked like a broken release.

This release is the verification and lifecycle layer the updater was missing. The
comparison point is Anthropic's `Claude Setup.exe` (`win32-bootstrapper`), which
separates four things AgentHub used to mix into one: whether the machine is
eligible, whether the file is genuine, where to look next when a source is blocked,
and how to report a failure. What was taken is that separation, not its MSIX/Appx
install path — AgentHub ships an NSIS installer through electron-builder, so what
matters is what happens before and after the download, not how the package is
installed.

- **An unverified file is never shown as verified.** `verifyFile` returns three
  states, not a boolean: `ok`, `mismatch`, and `unverified`. When a release has no
  `SHA256SUMS.txt`, the pane says "tanpa checksum — this release has no
  SHA256SUMS.txt, the file cannot be compared" in a warning badge. A green check
  for a file nobody compared is the same lie as accepting a corrupt one, and it is
  worse, because it teaches you to trust the checkmark.
- **A mismatched file is refused, not deleted.** Installing is blocked at the API
  (`409 CHECKSUM_MISMATCH`) and the pane prints both hashes, expected and actual.
  The file stays on disk on purpose: deleting the evidence is what makes the bug
  report impossible. Only the download is retried, and only for network errors —
  re-fetching the same bytes from the same proxy is a waste of time and quota.
- **Interception is diagnosed before checksums.** An `text/html`,
  `application/json`, or short body is reported as a proxy or captive portal with
  the bytes received versus expected, and a `.exe` that does not begin with `MZ` is
  named as such. This ordering matters: an HTML login page will never match a hash,
  and "checksum mismatch" would send you looking for a corrupt release when the real
  problem is your office firewall.
- **Preflight runs before 100 MB is downloaded.** Platform, architecture, Node
  version, free disk, and whether the data folder is writable — each with `ok`,
  `warn`, or `error`. Unknown free space is a `warn`, not an `error`: refusing to
  install because `statfs` failed on one platform would block a machine that is
  perfectly fine. The same check gates `POST /api/update/install`, because that
  endpoint can be called by an agent or `curl` with no UI at all.
- **Two sources, then the failure is named.** The release check tries the GitHub
  API with retry (exponential backoff plus jitter, so instances do not all hit the
  host in the same millisecond), then falls back to the download host. When every
  source fails, the pane lists each one that was tried and why it failed, instead of
  a single "failed" that leaves you guessing between network, firewall, and rate
  limit.
- **Diagnostics and uninstall are answers, not documentation.** `GET
  /api/diagnostics` produces one file you can attach to a bug report — runtime,
  update state, verification result, preflight findings, redacted config, engine and
  thread counts, and the last 200 log lines. Tokens and API keys are replaced with
  `[disembunyikan]`, never omitted, so their presence stays visible without leaking
  them. `GET /api/install/uninstall-plan` returns exactly what an uninstall removes:
  autostart entry, data folder, the app itself. Both are visible in the pane, since
  a plan you can only read in the source is not a plan.
- **The install lifecycle is a declared machine.** `checking → eligible →
  downloading → verifying → ready → installing`, with `blocked` reachable from
  `verifying` and back out again. `installing` can return to `ready` when the
  installer fails to spawn, because a state the UI cannot leave is a dead end.
  Machine contract version **5**.

Tests: `test/install.test.js` covers all six features (19 tests, pure logic plus a
local fixture server that serves a wrong checksum and an HTML page). The full suite
is green.
