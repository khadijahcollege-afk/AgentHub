# AgentHub 1.9.14

Tidak ada karakter aneh lagi di layar, dan ada penjaga agar tidak kembali.

## Masalahnya

Teks di UI muncul sebagai rangkaian karakter sampah alih-alih
`AgentHub — studio agent`.

Penyebabnya bukan bug di kode aplikasi, melainkan **cara saya menyunting berkas**
pada dua rilis sebelumnya. Beberapa berkas ditulis ulang lewat PowerShell:

```powershell
$c = Get-Content $f -Raw          # membaca UTF-8 TANPA BOM sebagai CP1252
[System.IO.File]::WriteAllText((Resolve-Path $f), $c)
```

`Get-Content -Raw` pada PowerShell 5.1 mendekode berkas sebagai code page ANSI
(CP1252) bila tidak ada BOM. Karena itu setiap em dash (U+2014) dipecah menjadi
tiga karakter, dan setiap middle dot (U+00B7) menjadi dua — lalu semuanya ditulis
kembali sebagai UTF-8 **yang sah**. Validasi encoding biasa tetap lolos;
kerusakannya hanya terlihat di layar.

## Kenapa berlapis

Berkas yang sama tersentuh lebih dari sekali, jadi kerusakannya menumpuk: satu
em dash bisa menjadi tiga karakter, lalu tiga karakter itu rusak lagi menjadi
sembilan. `index.html` di paket 1.9.13 mengandung **540** pola rusak; di 1.9.12
ada 144.

Karena itu pemulihan tidak dilakukan dengan membalik encoding berkali-kali
(hasilnya tidak utuh), melainkan mengambil blob git **sebelum** kerusakan masuk —
`HEAD~2`, yang masih bersih — lalu menerapkan hanya perubahan yang memang
disengaja (nomor versi dan cache-busting).

Dua berkas tes (`test/freerot.test.js`, `test/memory-extract-api.test.js`) sudah
rusak lebih lama dan tidak punya versi bersih di riwayat terdekat. Kerusakannya
seragam dan sempit: pola byte `c3 a2 e2 82 ac e2 80 9d` yang seharusnya
`e2 80 94` (em dash). Diperbaiki pada tingkat byte, lalu diverifikasi dengan
`node --check` bahwa sintaksnya tetap sah. Satu BOM juga dibuang dari
`test/memory-extract-api.test.js`.

## Penjaganya

Tes baru `test/encoding.test.js` memindai seluruh berkas teks repo (267 berkas)
dan memeriksa **byte**, bukan hasil decode — justru karena kerusakan ini
menghasilkan UTF-8 yang sah:

- tidak ada urutan byte mojibake (`c3 a2 e2 82 …`, `c3 82 c2 …`, dan seterusnya)
- tidak ada BOM di awal berkas teks
- semua berkas teks adalah UTF-8 sah

Pola di berkas tes ditulis sebagai byte eksplisit, bukan karakter literal — kalau
ditulis literal, berkas tes itu sendiri akan cocok dengan polanya. Itu sempat
terjadi dan langsung tertangkap.

Dibuktikan bekerja dengan menyuntikkan kerusakan sungguhan:

```
repo bersih        : HIJAU (benar)
dengan mojibake    : MERAH (benar)   <- test/_probe-encoding.test.js:1
dengan BOM         : MERAH (benar)
setelah dibersihkan: HIJAU (benar)
```

## Aturan untuk sesudah ini

Berkas repo tidak pernah lagi ditulis lewat `Get-Content -Raw` + `WriteAllText`.
Penyuntingan memakai `fs.readFileSync(p, 'utf8')` dan `fs.writeFileSync(p, t, 'utf8')`.
BOM tidak ditulis, karena BOM-lah yang membuat PowerShell salah menebak encoding.

## Catatan

1.9.13 sudah terbit dengan `index.html` yang rusak, jadi versi ini dirilis untuk
menggantikannya. Isi perbaikan pembaruan otomatis dari 1.9.13 (argumen `/S` tidak
boleh dikutip) tetap ada dan tidak berubah.

Suite: 694 tes, hijau.
